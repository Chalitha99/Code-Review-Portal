# Gap register

Two kinds of row: **spec items with no implementation to test** (nothing in
the running app exercises them, so no test case in `qa/test-cases/` covers
them — expected Fail/N/A if attempted), and the **inverse** — implemented
behaviour the spec never describes. Both matter for sign-off: the first tells
a reviewer why a spec clause has no test case ID in
[`traceability-matrix.md`](./traceability-matrix.md); the second is scope
creep or an undocumented capability that should be raised with whoever owns
the spec.

A third category is included for transparency: **spec wording that the app
does not match literally** (a toast the spec quotes but the code never
sends, a button label, a message string) even though the underlying
capability _is_ implemented. These are not gaps in coverage — a test case
exists and asserts the app's real behaviour — but the mismatch is worth a
single glance before anyone assumes the spec's quoted strings are still
authoritative for exact wording.

## How to use this register

- Executing a case from `qa/test-cases/` that touches a row in **A** is
  expected to be blocked or not applicable — record `N/A`, not `Fail`, and
  reference this register in the Notes column.
- A row in **B** found during exploratory testing but not listed here is a
  new inverse gap — add it to this table rather than filing it as a defect.
- A row in **C** is not a defect. If the app's real behaviour ever starts
  matching the spec's quoted wording, that's a welcome change — update the
  affected test case's Expected result and remove the row here.
