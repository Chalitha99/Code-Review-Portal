# TC-REV-review — Review Task Page (Code Review Form)

Covers spec 2.9 in full: 2.9.2.1 (My Review Tasks tab), 2.9.2.2 (Review Task Details Form + Back), 2.9.2.3 (Delivery/Developer Quality Check List Form, read-only), 2.9.2.4 (Code Review Form — General Check, Answer Evaluation Option, FL 2.9.2.4-01, FL 2.9.2.4-02), 2.9.2.5 (Review Ranking, FL 2.9.2.5-01), and 2.9.2.6 (Screenshot and Feedback Form, FL 2.9.2.6-01). The single page under test is `/crp/reviewer/tasks/:taskId` (`src/portals/code-review/features/reviews/routes/ReviewTaskPage.tsx`, form in `src/portals/code-review/features/reviews/components/CodeReviewForm.tsx`, blocking rules in `src/portals/code-review/features/reviews/domain/reviewRules.ts`). Primary user: Hiruni Wijethilaka (hiruni.wijethilaka@sebsaworld.com), Reviewer role, reviewing tasks submitted by other developers (e.g. Janukshan Sivakumar).

Implementation facts verified against source before writing this file (read, not assumed):

- **General Check has 13 questions** (`src/mocks/data/generalCheck.json`, ids `gc-1`..`gc-13`), confirming the spec's "section 3.1 General Check" count. Labelled in the form as "3.1 General Check" with an "Answered n/13" tag.
- The **Answer Evaluation Option control** is a 4-way segmented radio per question: **OK / Partially OK / Not OK / N/A** (`common.json` `generalCheckAnswer`, rendered by `GeneralCheckPicker` in `src/portals/code-review/components/checklist.tsx`). "OK" and "Not OK", not spec's occasionally-used "Yes/No" wording from the Developer Checklist (that Yes/No/N/A control is a _different_ control, used only on the read-only Developer Quality Checklist section, not on the reviewer's own General Check).
- **Detailed Review Findings** (spec's "3.2") is actually **three separate text boxes**: "Incorrect Code and Performance-Related Issues", "Incomplete Implementation", "Source Code Formatting, Naming, Comments, Indentation and Readability" — any one of the three having non-blank text satisfies "findings provided" (`hasFindings` in `reviewRules.ts`).
- Validation is **not** a submit-then-toast flow as spec 2.9.2.4/2.9.2.5 Functional Logic implies. Instead `reviewBlockers()` runs live on every keystroke: the Approve and Request Changes buttons stay **disabled** while blockers exist, and an inline warning box ("Before you can submit this review") lists the outstanding items using these **actual UI strings** (`reviews.json` `form.blockers`), which are shorter than the spec's quoted Functional-Logic messages:
  - `generalCheckIncomplete`: "Answer every General Check question" (spec FL 2.9.2.4-01 message: "All General Check items must be evaluated before submitting the review.")
  - `findingsRequired`: "Describe the issues in Detailed Review Findings" (spec FL 2.9.2.4-02 message: "A valid explanation must be provided in Detailed Review Findings when an item is marked as Partially OK or Not OK.")
  - `rankRequired`: "Choose a review ranking"
  - `screenshotRequired`: "Attach at least one screenshot"
  - `approveBlockedByRank`: shown separately as its own danger alert: "Approve is not available at Rank 2 or Rank 3 — request changes instead" (spec FL 2.9.2.5-01 message: "Rank 2 or 3 reviews require detailed findings and uploaded issue screenshots. Please click 'Request Changes' once completed.") — this exact mismatch is logged for the gap register; test cases below assert the real UI text.
  - The server (`PUT /api/tasks/:taskId/review` in `src/mocks/handlers.ts`) re-runs the same `reviewBlockers` check and returns 422 `"Complete the review before submitting it."` or (for the rank block specifically) `"A Rank 2 or Rank 3 review cannot be approved. Request changes instead."` — in normal use this is unreachable because the buttons are already disabled, but is included as a defence-in-depth case.
- **Screenshot limits**: PNG/JPG/GIF/WebP, 5MB max per file, 10 max total — confirmed against `packages/contracts/src/enums.ts` (`MAX_SCREENSHOT_BYTES = 5 * 1024 * 1024`, `MAX_SCREENSHOTS_PER_REVIEW = 10`). The rejection messages actually rendered come from `common.json` `dropzone.imageRejected` (the live component, `ImageDropzone.tsx`, reads `common.json` not `reviews.json`; `reviews.json`'s near-duplicate `screenshotRejected` block is unused dead content): `"{fileName} is larger than 5MB."`, `"{fileName} is not a PNG, JPG, GIF or WebP image."`, `"You can attach at most 10 images."` — the last one says "images", not spec's phrasing. The "Select Screenshots" button label matches spec's RMB name exactly.
- **Per-image comments** exist: each uploaded screenshot has its own caption textbox (`aria-label="Caption for {fileName}"`), saved on blur.
- **Feedback Summary character counter**: max length is **10,000** characters (`MAX_FEEDBACK_SUMMARY_CHARS` in `packages/contracts/src/enums.ts`), enforced via `maxLength` + `showCount` on the Summary Comments textarea. (Do not confuse with the separate, uncapped "Total Feedback Length" counter under Other Remarks, which sums the three findings boxes + Other Remarks and has no enforced max.)
- **Autosave-as-draft** genuinely exists (`ReviewFormSection` in `ReviewTaskPage.tsx`): edits are saved via `PUT /api/tasks/:taskId/review` 800ms after the reviewer stops typing (and once more on unmount/navigate-away), with `decision` left unset so the task stays "In Review" — this is a running draft of the _review_, not a task-level "Draft" status change, and it is silent (no toast) by design.
- **Approve** sets task status to "Approved" and does not change the review cycle. **Request Changes** sets task status to "ChangesRequested", increments `reviewCycle` by 1, and clears the task's `reviewerId` (returns to the developer, then the queue). Confirmed in `handlers.ts`.
- The **Handover** button appears on this page only while the review `isEditable` (i.e. still assigned to the current reviewer and not yet decided) — see `TC-HAND-handover.md` for handover cases; not duplicated here.
