# TC-REV-dashboard — Reviewer Workspace & Dashboard

Covers spec 2.7 (Review of Workspace & Dashboard), 2.8 (Available Tasks Tab), FL 3.3-01 (Task Pickup & Ownership Transition) and FL 3.3-02 (Concurrent Pick Handling). Scope is `/crp/reviewer` (Reviewer Dashboard root = Available Tasks tab), its four KPI cards, the four tabs, the filter bar, the Pick action, the server-side self-review bar, and the concurrent-pick race. Primary users: any of the 9 active Developer+Reviewer+Admin seeded accounts (e.g. hiruni.wijethilaka@sebsaworld.com, charith.widanapathirana@sebsaworld.com). The negative case for role access uses dheliya.kankanamge@sebsaworld.com (Developer only).

Implementation notes verified against source before writing this file:

- The Reviewer Dashboard has **4** tabs (`src/portals/code-review/features/reviews/routes/ReviewerLayout.tsx`, `src/content/reviews.json` `workspace.tabs`): **Available Tasks**, **My Review Tasks**, **Review History**, **Analytics**. Spec 1.5 says "3 main tabs" (Available/My Review/Review History) — Analytics is an implemented fourth tab not mentioned in that sentence. Analytics itself is out of scope for this file.
- The 4 KPI cards (`ReviewerLayout.tsx`, `reviews.json` `kpis`) are: **Available Tasks**, **My In Review**, **Changes Requested**, **Reviews Approved**. The first two are live counters that also act as tab-opening controls (no extra status filter); the last two count decided _reviews_, not tasks, and are static (not clickable filters).
- The filter bar actually implemented (`src/portals/code-review/components/TaskFilterBar.tsx`, `taskFilters.ts`) is **one free-text Search field** (labelled "Search ID, title, CRIM…", matches Task ID / Title / CRIM ID / Customer) plus **Status**, **Priority**, and (History tab only) **Cycle** dropdowns. There is **no separate Task ID, Title, CRIM ID, Customer, or Developer filter field** — spec 2.7.3/2.8.3 field tables and spec 1.5's filter list ("Task ID, Title, CRIM ID, Priority, Customer, and Developer") are not matched field-for-field; Developer is not filterable at all on any reviewer tab. `reviews.json`'s `available.filters` (customer/developer/priority labels) exists in content but is unused dead content — grep confirms no component reads it. This is flagged for the gap register; cases below test the filter bar as it actually exists.
- Pick / self-review bar: `src/mocks/handlers.ts` `POST /api/tasks/:taskId/pick` enforces `task.developerId === user.id → 403 FORBIDDEN "You cannot review a task you submitted."` server-side, and the `GET /api/tasks?scope=available` handler filters out the caller's own submissions before the list even reaches the client. Confirmed implemented, not just spec'd.
- FL 3.3-01 toast: `reviews.json` `available.picked` = `"{taskCode} is yours. It is now In Review."` (interpolated with the real task code) — not literally the spec's wording, which is unspecified verbatim anyway.
- FL 3.3-02 message: the **real** server message (`errorResponse(409, 'ALREADY_PICKED', ...)` in `handlers.ts`) is **`"{reviewer name} has already picked up this task."`** (e.g. "Hiruni Wijethilaka has already picked up this task.") when a reviewer is on it, or `"This task is no longer available."` if the reviewer became null for another reason. This differs from the spec's placeholder text `"Task [Task ID] has already been claimed by another reviewer."` — the app names the reviewer, not the Task ID. Test case below asserts the real message; the mismatch is noted for the gap register.
