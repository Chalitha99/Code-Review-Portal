# TC-HAND-handover — Handover Process (Reviewer Hand Over + Admin Handovers Tab)

Covers the spec's prose "Handover Process" section (p.12, under 1.5 Reviewer Workspace functionality) and the Admin Workspace "Handover Task Tab" prose (p.13, under 2.12 Admin Workspace). Involves the reviewer-side "Hand Over" action on the Review Task page (`src/portals/code-review/features/reviews/components/HandoverDialog.tsx`) and the admin-side Handovers tab at `/crp/admin/handovers` (`src/portals/code-review/features/admin/routes/AdminHandoversPage.tsx`, `ReassignHandoverDialog.tsx`, `src/mocks/handlers.ts` handover endpoints). Two accounts are used across the sequence: a Reviewer (Hiruni Wijethilaka, hiruni.wijethilaka@sebsaworld.com) and the Admin (Janith Hasthanayake, janith.hasthanayake@sebsaworld.com, who also holds Admin among his roles).

**Important — per shared context DB rules**: the in-memory mock DB rebuilds from seed on every browser reload (F5), and sign-out does NOT reset it. Every multi-step case below that spans a reviewer action followed by an admin action requires **signing out of one account and signing in as the other, with no page reload at any point in the sequence** (reload discards the handover just created). Each case's Preconditions states this explicitly.

Implementation facts verified against source before writing this file:

- The spec describes only **one** admin handover action: "The admin then selects the respective reviewer's name and clicks 'OK.'" (Reassign). The **actual app also implements a second action, "Return to Queue"** (`Undo2` icon, `admin.json` `handovers.actions.return` = "Return {taskCode} to the open queue", `POST /api/handovers/:handoverId/return`), which puts the task straight back into the open Available Tasks queue for any reviewer to pick up, with no reviewer named. This is confirmed present in the running code and is an **app-only addition beyond the spec** — not a hallucinated feature, but also not something the spec describes; the field-table label the app actually uses is "Reassign" for the dialog's submit button, not literally "OK" as spec 2.12/Handover Task Tab prose states — this wording mismatch is also logged for the gap register.
- Admin dialog button label is "Reassign" (`admin.json` `handovers.reassign.submit`), not "OK" as spec prose states — logged for the gap register alongside the point above.
- `POST /api/tasks/:taskId/handover` clears `task.reviewerId`, sets `task.isHandedOver = true`, and does **not** touch `reviewCycle`. While `isHandedOver` is true the task is excluded from the open Available Tasks queue (confirmed in the `scope=available` filter: `!t.isHandedOver`), so it is genuinely in limbo — visible only in the Admin Handovers tab — until an admin acts.
- Reassign excludes two people from the reviewer picker (`ReassignHandoverDialog.tsx`): the reviewer who handed the task over, and the developer who submitted it (self-review bar). If no other active Reviewer exists, the Select is disabled and "No other active reviewer is eligible for this task." is shown.
- Email: a handover emails every active Admin and Super Admin and the developer (reason, time, task code and customer); an admin reassignment emails the new reviewer and the developer. See `docs/email-notifications.md`.
- A resolved handover (Reassigned or Cancelled/Returned) stays listed in the Handovers grid rather than disappearing, with its Reassign/Return action buttons hidden — the grid is a history, not just a live queue.
